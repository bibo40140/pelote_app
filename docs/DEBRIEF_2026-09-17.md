# PELOTE_APP - Débrief du 17 septembre 2026

## 1. Situation du projet

Le socle de PELOTE_APP est opérationnel.

L’application dispose actuellement :

- d’une base PostgreSQL Supabase ;
- de l’authentification Supabase ;
- d’un compte administrateur actif ;
- des politiques Row Level Security ;
- des fonctions SQL sécurisées ;
- d’une interface React avec routes protégées ;
- des principaux référentiels administratifs ;
- de données fictives suffisantes pour réaliser les tests ;
- d’une gestion des périodes, des créneaux, des disponibilités récurrentes et des exceptions.

---

## 2. Décision métier importante

Dans la V1, une discipline correspond directement à une pratique complète.

Exemples :

- Trinquet gomme pleine ;
- Trinquet gomme creuse ;
- Mur à gauche gomme pleine ;
- Mur à gauche cuir ;
- Place libre gomme pleine.

Les types d’installation restent utilisés pour catégoriser les installations physiques et pour le planning.

Exemples :

- type Trinquet ;
- type Mur à gauche ;
- type Place libre.

Les installations correspondent aux lieux physiques :

- Enea ;
- Besson - Trinquet ;
- Besson - Mur à gauche ;
- Saint-Geours ;
- Saint-Paul ;
- Dax.

La piste consistant à ajouter `installation_type_id` dans les inscriptions, équipes et compétitions a été abandonnée.

Aucune migration de modèle de pratique ne doit être créée.

Cette migration met en place les fonctions sécurisées, notamment :

- création ou modification des disponibilités ;
- correction administrative des disponibilités ;
- création des exceptions initiales ;

- amorçage du premier administrateur ;

État :

- exécutée avec succès après correction d’un `SELECT INTO` incompatible avec une variable `%ROWTYPE`.

### `004_availability_exceptions.sql`

Cette migration fait évoluer les exceptions afin qu’elles puissent être renseignées avant la création du planning.

Le nouveau modèle prévoit :

#### Exception ponctuelle

Une exception ponctuelle porte sur :

- un joueur ;
- un créneau récurrent ;
- une date précise ;
- un état disponible ou indisponible ;
- un motif facultatif.

Exemple :

> Disponible habituellement le lundi de 21 h à 22 h, sauf le lundi 21 septembre.

#### Absence sur une période

Une absence sur une période porte sur :

- un joueur ;
- une date de début ;
- une date de fin ;
- un motif facultatif.

Exemple :

> Indisponible du 10 au 20 octobre pour vacances.

#### Priorité prévue pour le futur planning

1. Une absence globale active couvrant la date rend le joueur indisponible.
2. Sinon, une exception ponctuelle active remplace la disponibilité récurrente.
3. Sinon, la disponibilité récurrente s’applique.

#### État technique à vérifier

La migration a rencontré plusieurs erreurs pendant les essais :

- suppression d’une policy inexistante ;
- tentative d’ajout d’une colonne `training_slot_id` déjà présente.

Malgré ces erreurs, les fonctionnalités d’exception semblent fonctionner dans l’application.

Avant de clôturer définitivement la migration 004, il faudra :

- inspecter l’état réel de `availability_exceptions` dans Supabase ;
- vérifier ses colonnes ;
- vérifier ses contraintes et index ;
- vérifier ses policies ;
- vérifier les signatures et permissions des trois RPC ;
- rendre le fichier `004_availability_exceptions.sql` reproductible depuis une base ayant uniquement exécuté 001, 002 et 003 ;
- tester si possible la reconstruction sur une base locale ou un environnement de test propre.

Cette vérification est prioritaire avant une mise en production, mais elle ne bloque pas les tests d’interface actuels.

## 5. Modules administratifs réalisés

Les modules suivants sont disponibles :

- Joueurs ;
- Saisons ;
- Disciplines ;
- Séries ;
- Types d’installation ;
- Installations ;
- Équipes ;
- Périodes d’entraînement ;
- Créneaux d’entraînement.

### Joueurs

Le module permet notamment :

- la création d’un joueur ;
- la modification de ses informations ;
- la désactivation logique ;
- l’inscription à une discipline pour une saison et une série ;
- plusieurs inscriptions dans différentes disciplines.

### Équipes

Le module permet notamment :

- la création d’une équipe ;
- la sélection d’une saison ;
- la sélection d’une discipline ;
- la sélection d’une série de référence ;
- la sélection des deux membres ;
- l’archivage ;
- la consultation des membres.

Les joueurs peuvent être filtrés selon leur inscription.

Le même joueur ne doit pas être sélectionné deux fois.

Un joueur déjà engagé dans une équipe active de la même saison et discipline ne doit plus être proposé.

### Périodes

Le module permet :

- la création ;
- la modification ;
- les changements de statut ;
- l’ouverture des disponibilités.

Un joueur ne voit les créneaux dans « Mes disponibilités » que lorsque la période est au statut `AVAILABILITIES_OPEN`.

### Créneaux

Le module permet :

- la création unitaire ;
- la modification ;
- l’archivage ;
- la création en grille hebdomadaire.

La grille permet de sélectionner :

- une période ;
- une discipline ;
- une installation ;
- une plage horaire d’affichage ;
- plusieurs cellules jour/horaire.

Les créneaux peuvent commencer le matin ou se poursuivre jusqu’en soirée.

Les installations restent affichées explicitement, car le lieu peut modifier la disponibilité réelle du joueur.

Le joueur peut, pour chaque créneau :

- ne fournir aucune réponse ;
- se déclarer disponible ;
- indiquer un horaire préféré ;
- se déclarer indisponible.

Le changement d’état s’effectue directement depuis la grille.
